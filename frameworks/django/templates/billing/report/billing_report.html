One count() and one sum() over the invoices that are not settled — two aggregates in one statement, and the figure the rest of this page is measured against.

Money is stored here as a whole number of CENTS, which is exact on every engine including the ones with no decimal type, and turned into something a person reads through Decimal in one place rather than in each page. Orders stores the same kind of value as a NUMERIC(12,2); both are defensible and the conversion between them lives in a single function.

Every plan, including the ones nobody is on

annotate(subscription_count=count(Plan.subscriptions)) — the aggregate came back in the SAME statement as the plan, so a tariff with no subscribers still appears with a zero. That is exactly the row a GROUP BY over the subscriptions would have dropped, and the one a "which tariffs are dead" question is about.

The plans that have actually invoiced

group_by(Plan.name).having(sum(...) >= {{ minimum }}) — the engine filtered an aggregate BY that aggregate, so a plan under {{ minimum }} never left the database. There is no id on these rows: the rows were folded on the plan's NAME, so there is no single plan row left to take one from, and the shape says so instead of inventing one.

The oldest debts still open

snake_date_add(Invoice.issued_at, 30, DAY) — the due date is computed by the ENGINE, so it can be projected, compared and ordered by without a single row leaving the database. Thirty DAYS and not one month: "net 30" is counted in days, and days are the unit the three engines agree on — SQLite overflows a calendar month.

snake_cast(collected, float) / snake_cast(amount, float) — both columns are integer cents, so without the cast this is integer division and every partly-paid invoice reads 0%. The collected figure is a correlated SUM over that invoice's payments, in the SAME statement: asking per row would be an N+1.
