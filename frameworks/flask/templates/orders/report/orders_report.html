The biggest and the newest, in one result

A compound: "the largest orders" UNION "the most recent ones", each branch keeping its own LIMIT. This is the one figure on the page that depends on the engine rather than on the data, so the page says which path ran instead of hiding it.

This engine allows a compound's branches to be parenthesised, so each one keeps its own LIMIT and the whole thing went to the database as one statement.

{% else %}

This engine answers Cap.PARENTHESISED_COMPOUND with Nope — SQLite refuses parentheses around a compound's branches, and without them a branch cannot keep its own LIMIT. So the two branches ran as two statements and were folded in Python. The result is the same rows; the cost is one extra round trip, and this is what "declare what the engine cannot do" looks like from the page.

No customer and no warehouse on these rows, and that is not an omission: a compound loads no relationships — an include on a branch is refused when the compound is built — so the rows arrive knowing their own columns and nothing else. Flattening a relation here would be a query per highlight.

What is on each order

string_agg(OrderLine.sku.name, ", ", order_by=[...]) — the engine folds a to-many into ONE cell. Before this, that column cost a second query and a grouping pass in Python, or a walk over order.lines in the template — the N+1 that does not look like one because it looks like reading an attribute.

The order_by lives INSIDE the aggregate. Without it the engine concatenates in whatever order it read the rows, so the same page can say Gamma, Alpha on one run and something else on the next.
